# yngmin's Decision Making Principles (Korean) - v1 (260709)

## 0. 문서의 목적

본 문서는 특정 기술, 프레임워크 또는 프로젝트에 종속되지 않는 의사결정 원칙을 정의한다.

기술 스택은 시간이 지나며 바뀔 수 있다. 프레임워크도 바뀔 수 있다. 프로젝트 구조도 바뀔 수 있다. 하지만 설계와 구현 과정에서 무엇을 중요하게 생각하고, 어떤 기준으로 선택하며, 어떤 비용을 줄이려 하는지는 상대적으로 오래 유지된다.

본 문서는 특정 상황에서의 정답을 제공하지 않는다. 대신 여러 선택지 사이에서 어떤 기준으로 판단할 것인지를 정의한다.

본 문서의 원칙은 실제 운영, 유지보수, 협업, 반복적인 개선 과정에서 드러난 의사결정 패턴을 일반화한 것이다. 특정 프로젝트의 사례를 직접 설명하지 않고, 여러 상황에 적용 가능한 판단 기준으로 정리한다.

또한 본 문서는 완성된 정답이나 보편적인 개발 규칙을 주장하기 위한 문서가 아니다. 아직 배우고 있는 입장에서 직접 구현하고, 운영하고, 문제를 겪고, 다시 수정하면서 얻은 현재의 판단 기준을 정리한 문서에 가깝다. 따라서 이 원칙들은 고정된 결론이 아니라, 더 나은 경험과 근거가 쌓이면 수정될 수 있는 작업 기준이다.

## 1. 유지보수 비용을 기능 구현 비용만큼 중요하게 본다

### 원칙

좋은 구현은 빠르게 완성된 구현이 아니다.

좋은 구현은 미래의 수정 비용이 낮은 구현이다.

대부분의 코드는 작성보다 수정에 더 많은 시간이 사용된다. 따라서 구현 시점의 편의성보다 이후 변경 비용을 함께 고려한다.

### 판단 기준

다음 질문들은 구현 이전 단계에서 검토 대상이 된다.

- 이 코드는 나중에 수정하기 쉬운가
- 변경 범위가 명확하게 격리되는가
- 새로운 요구사항이 들어왔을 때 기존 코드를 얼마나 건드려야 하는가
- 변경 이유가 서로 다른 코드가 섞여 있지는 않은가
- 지금 편한 구현이 나중에 더 큰 비용이 되지는 않는가

### 적용 방식

처음부터 완벽한 구조를 만들려고 하지는 않는다. 다만 변경 가능성이 높은 지점은 최소한의 분리 기준을 확보한다.

특히 다음 영역은 변경 비용을 먼저 고려한다.

- 데이터 구조
- 외부 서비스 연동부
- 설정값
- 사용자 입력 처리
- 저장소 접근 방식
- 알림 또는 후속 처리 흐름

### 경험 기반 사례

실제 운영되는 백그라운드 애플리케이션을 만들면서, 기능 구현만으로는 충분하지 않다는 것을 확인했다. 신규 개발자 또는 운영자가 구조를 빠르게 파악할 수 있도록 아키텍처, 데이터베이스, 설정, 배포, 운영 문서를 분리했다.

이는 문서를 별도로 만들기 위한 문서화가 아니라, 나중에 코드를 다시 읽거나 다른 사람이 운영 흐름을 이해해야 할 때 발생하는 비용을 줄이기 위한 선택이었다.

### 예외

프로토타입, 검증용 코드, 일회성 스크립트에서는 유지보수성보다 구현 속도를 우선할 수 있다.

단, 일회성 코드가 장기 운영 코드로 전환될 가능성이 있다면 초기에 최소한의 구조를 잡아둔다.

## 2. 역할보다 변경 이유를 기준으로 분리한다

### 원칙

구성 요소는 구현 위치보다 변경 이유를 기준으로 분리한다.

같은 이유로 변경되는 코드는 함께 위치하는 것이 좋다. 다른 이유로 변경되는 코드는 가능한 분리하는 것이 좋다.

관심사는 파일 구조보다 중요하다. 레이어 구조보다 변경 이유가 우선한다.

### 판단 기준

다음 질문을 사용한다.

> 이 코드는 왜 존재하는가
> 

그리고

> 이 코드는 무엇 때문에 변경될 것인가
> 

역할 이름만 보고 배치하지 않는다. `service`, `manager`, `repository`, `handler` 같은 이름은 보조적인 단서일 뿐이다.

핵심은 해당 코드가 어떤 변경 압력을 받는지 파악하는 것이다.

### 적용 방식

다음 변경 이유는 가능한 분리한다.

- 비즈니스 정책 변경
- 저장 방식 변경
- 외부 API 변경
- 입력 형식 변경
- 출력 형식 변경
- 운영 정책 변경
- 사용자 인터페이스 변경

### 경험 기반 사례

사용자 이벤트를 처리하는 계층과 외부 서비스 및 저장소에 접근하는 계층을 분리하는 방향을 잡았다. 이벤트 처리 코드는 흐름 제어에 집중하고, 외부 API 호출과 데이터 접근은 별도 계층에 위임하는 구조를 의도했다.

다만 실제 코드가 항상 이상적인 구조를 만족한 것은 아니다. 일부 이벤트 처리 코드는 필터링, 언어 처리, 사용자 정보 추출, 외부 연동 호출까지 많은 책임을 가지고 있었다. 이 경험을 통해 레이어 이름 자체보다 변경 이유와 책임 범위를 기준으로 리팩터링 대상을 판단해야 한다는 기준이 더 명확해졌다.

### 예시

데이터를 가져오는 코드와 데이터를 해석하는 코드는 서로 다른 이유로 변경될 수 있다.

저장소 접근 방식이 바뀌는 것과 비즈니스 판단 기준이 바뀌는 것은 같은 문제가 아니다. 따라서 둘을 같은 위치에 넣기보다 변경 이유에 따라 분리한다.

## 3. 운영 비용은 개발 비용만큼 중요하다

### 원칙

개발자는 기능을 만드는 사람인 동시에 시스템을 운영하는 사람이기도 하다.

운영 과정에서 반복적으로 발생하는 작업은 시간이 지날수록 누적 비용이 된다. 작은 수동 작업도 서비스 규모와 운영 기간이 증가하면 상당한 부담이 될 수 있다.

### 프로젝트에서 드러나는 일반적인 상황

초기에는 사람이 직접 처리해도 되던 작업들이 운영 규모가 커지면서 반복적으로 발생한다.

예를 들면 다음과 같은 작업이 있다.

- 사용자 요청 처리
- 데이터 저장
- 외부 서비스 연동
- 상태 추적
- 운영자 알림
- 반복적인 정리 작업

개별 작업은 작을 수 있다. 하지만 장기적으로 반복되면 개발 시간보다 더 큰 운영 비용을 만들 수 있다.

### 판단 기준

다음 질문을 사용한다.

- 이 작업은 반복되는가
- 사람이 직접 처리해야만 하는가
- 실수했을 때 영향 범위가 큰가
- 자동화 비용보다 반복 비용이 커질 가능성이 있는가
- 운영자가 개입하지 않아도 되는 구조로 만들 수 있는가

### 적용 방식

반복적으로 수행되는 운영 작업은 자동화를 우선 검토한다.

특히 다음 작업은 자동화 후보로 본다.

- 데이터 동기화
- 캐시 갱신
- 알림 발송
- 상태 확인
- 로그 정리
- 중복 검사
- 실패 작업 재시도

### 경험 기반 사례

외부 서비스에 첨부파일을 동기화할 때 모든 파일을 그대로 업로드하지 않았다. 파일을 로컬에 다운로드하고 외부 API에 다시 업로드하는 과정은 서버 리소스와 네트워크 비용을 증가시키기 때문에, 실제 확인 가치가 높은 이미지 파일만 직접 업로드하고 나머지는 원본 메시지 링크로 대체했다.

사용자 입장에서는 모든 첨부파일이 외부 서비스에 직접 올라가는 것이 더 편할 수 있다. 하지만 운영 비용, 서버 리소스, 네트워크 사용량, 장애 가능성을 고려하면 모든 파일을 동일하게 처리하는 것이 항상 좋은 선택은 아니었다. 이 경험을 통해 사용자 경험과 운영 비용 사이에서 비용 대비 효과를 기준으로 범위를 제한하는 판단이 필요하다는 것을 확인했다.

### 예외

초기 검증 단계에서는 자동화 비용이 운영 비용보다 클 수 있다. 이 경우 수동 운영을 허용하되, 반복 발생 여부를 관찰한다.

반복성이 확인되면 자동화를 다시 검토한다.

## 4. 시스템은 사용자의 실수를 전제로 설계한다

### 원칙

사용자는 예상하지 못한 행동을 한다. 운영자도 실수한다. 개발자 자신도 실수한다.

따라서 시스템은 올바른 사용만을 전제로 설계하지 않는다.

안정적인 시스템은 정상 동작보다 실패 시 행동이 더 중요할 때가 많다.

### 프로젝트에서 드러나는 일반적인 상황

실제 사용 환경에서는 예상하지 못한 상황이 반복적으로 발생한다.

- 동일한 요청이 여러 번 들어온다
- 이미 존재하는 데이터가 다시 생성된다
- 일부 작업만 성공하고 나머지는 실패한다
- 잘못된 입력이 들어온다
- 외부 서비스 상태와 내부 상태가 어긋난다
- 사용자가 예상한 순서대로 행동하지 않는다

정상 흐름만 기준으로 설계하면 이런 상황에서 시스템이 쉽게 깨진다.

### 판단 기준

다음 질문을 사용한다.

- 잘못된 입력이 들어오면 어떻게 되는가
- 동일한 요청이 여러 번 들어오면 어떻게 되는가
- 실패한 작업이 다시 실행되면 문제가 발생하는가
- 운영자가 잘못된 설정을 적용하면 어떻게 되는가
- 일부 작업만 성공했을 때 복구 가능한가
- 중복 데이터가 생겨도 시스템이 버틸 수 있는가

### 적용 방식

가능하면 다음 성질을 확보한다.

- 중복 요청에 안전한 처리
- 입력값 검증
- 명확한 예외 처리
- 실패 상태 기록
- 재시도 가능성
- 수동 복구 가능성

### 경험 기반 사례

동일 사용자가 짧은 시간 안에 반복 요청을 보낼 수 있다고 보고, 마지막 상호작용 시간을 저장해 쿨다운 판단에 사용했다. 이는 사용자의 반복 클릭이나 실수로 인한 중복 생성, 외부 서비스 과호출, 운영 데이터 꼬임을 줄이기 위한 방어적 설계였다.

또한 운영자가 수정해야 하는 설정과 개발자가 관리해야 하는 내부 설정을 분리했다. 외부 연동 토큰, 실행 모드, DB 버전처럼 운영 환경에서 바뀔 수 있는 값은 런타임 설정으로 두고, 경로, 기본 동작, 내부 매핑처럼 시스템 기준이 되는 값은 내부 설정으로 분리했다.

이 구조는 운영 중 실수로 내부 동작 기준이 변경되는 위험을 줄이고, 변경 책임을 명확히 하기 위한 선택이었다.

## 5. 장애 가능성이 높은 경로를 먼저 설계한다

### 원칙

성공 경로는 대부분 자연스럽게 구현된다.

실제 운영 환경에서 문제를 만드는 것은 실패 경로다. 따라서 성공 흐름만 먼저 구현하고 실패 처리를 나중에 붙이는 방식을 경계한다.

성공은 기능이다. 실패 처리는 설계다.

### 프로젝트에서 드러나는 일반적인 상황

실제 장애 대부분은 핵심 로직 자체보다 외부 의존성, 네트워크, 데이터 상태 차이에서 발생한다.

대표적인 실패 지점은 다음과 같다.

- 외부 API 실패
- 네트워크 타임아웃
- 데이터베이스 접근 실패
- 데이터 불일치
- 중복 요청
- 부분 성공 상태
- 권한 문제
- 예상보다 느린 응답

### 판단 기준

다음 질문을 사용한다.

- 이 작업이 실패하면 어떤 상태가 남는가
- 실패한 작업은 다시 실행해도 안전한가
- 실패 사실을 추적할 수 있는가
- 사용자는 실패 상태를 알 수 있는가
- 운영자는 복구할 수 있는가
- 실패가 다른 기능으로 전파되는가

### 적용 방식

실패 가능성이 높은 작업은 다음 요소를 함께 설계한다.

- timeout
- retry
- fallback
- logging
- alert
- rollback 또는 compensation
- idempotency

### 경험 기반 사례

배포 자동화 과정에서 동일 시점에 여러 배포가 겹칠 가능성을 고려했다. 워크플로우 레벨에서는 동시 실행을 제한하고, 서버 내부에서는 배포 락을 사용해 중복 실행을 방지했다.

또한 재시작 스크립트는 단순히 프로세스를 다시 실행하는 데서 끝나지 않도록 구성했다. 기존 프로세스 종료, 강제 종료 fallback, 로그 디렉토리 생성, 백그라운드 실행, 기동 여부 확인, 실패 시 최근 로그 출력까지 포함했다.

이 경험을 통해 자동화는 실행 자체보다 실패 후 상태를 통제하는 것이 더 중요할 수 있다는 기준을 갖게 되었다.

### 예외

모든 실패 경로를 완벽하게 처리할 수는 없다. 중요도와 발생 가능성을 기준으로 우선순위를 정한다.

---

## 6. 현재 요구사항만 보지 않는다

### 원칙

과도한 미래 설계는 피한다. 하지만 미래 변경 가능성을 완전히 무시하지도 않는다.

현재 구현이 미래의 변경을 지나치게 어렵게 만든다면 최소한의 확장 지점을 확보한다.

목표는 완벽한 미래 예측이 아니다. 목표는 미래 변경 비용을 낮추는 것이다.

### 판단 기준

다음 질문을 사용한다.

- 이 요구사항은 일회성인가, 반복될 가능성이 있는가
- 같은 유형의 기능이 나중에 추가될 가능성이 있는가
- 데이터 구조가 바뀔 가능성이 있는가
- 외부 정책이나 API 변경에 영향을 받는가
- 지금 단순하게 만들면 나중에 전체 구조를 갈아엎어야 하는가

### 적용 방식

초기부터 모든 확장성을 구현하지 않는다.

대신 다음 정도의 확장 가능성을 확보한다.

- 설정값 분리
- 상수화
- 데이터 구조의 명확화
- 외부 의존성 격리
- 처리 단계 분리
- 명확한 인터페이스

### 경험 기반 사례

데이터베이스 구조 변경에 대비해 DB 내부에 버전 정보를 저장했다. 초기 단계에서는 정교한 마이그레이션 도구를 도입하지 않고, 버전 불일치 시 기존 데이터를 읽어 재구성하는 방식으로 대응했다.

이 방식은 완전한 해결책은 아니었다. 하지만 당시 데이터 규모와 운영 조건에서는 복잡한 마이그레이션 시스템보다 낮은 비용으로 구조 변경에 대응하는 것이 더 현실적인 선택이었다.

### 예외

아직 반복성이 확인되지 않은 기능은 과도하게 일반화하지 않는다.

같은 패턴이 두 번 이상 반복되거나, 변경 가능성이 명확할 때 구조화를 강화한다.

---

## 7. 자동화할 수 있는 작업은 자동화를 우선 검토한다

### 원칙

사람은 반복 작업에 약하다.

반복 작업은 실수를 만든다. 반복 작업은 집중력을 소모한다. 반복 작업은 지루함을 만든다.

따라서 반복 작업은 가능한 시스템이 처리하도록 만든다.

### 판단 기준

다음 질문을 사용한다.

> 이 작업은 사람이 직접 해야 하는가
> 

그리고

> 자동화하지 않았을 때 장기적으로 어떤 비용이 누적되는가
> 

### 적용 방식

자동화 대상은 다음 조건을 기준으로 판단한다.

- 반복 빈도가 높다
- 사람이 처리할 때 실수 가능성이 있다
- 처리 기준이 명확하다
- 작업 결과를 검증할 수 있다
- 실패해도 복구할 수 있다
- 장기적으로 운영 비용을 줄인다

### 보완 원칙

자동화는 사람이 하던 작업을 대신 실행하는 것만으로 충분하지 않다. 자동화가 실패했을 때 어떤 상태가 남는지, 다시 실행해도 안전한지, 운영자가 원인을 확인할 수 있는지가 함께 설계되어야 한다.

따라서 배포, 동기화, 재시작처럼 시스템 상태를 바꾸는 자동화는 중복 실행 방지, 실행 결과 검증, 실패 로그, 수동 복구 가능성을 함께 고려한다.

### 주의점

자동화는 무조건 좋은 것이 아니다.

기준이 불명확한 작업을 억지로 자동화하면 오히려 디버깅 비용이 늘어난다. 자동화는 반복성이 확인되고 판단 기준이 명확할 때 가장 효과적이다.

---

## 8. 구현 단순성을 우선한다

### 원칙

복잡한 구조는 복잡한 문제를 해결하기 위해서만 존재해야 한다.

복잡함 자체는 가치가 아니다. 동일한 문제를 해결할 수 있다면 더 단순한 구조를 우선 선택한다.

### 판단 기준

다음 조건을 만족한다면 단순한 구조를 우선한다.

- 동일한 기능 제공
- 동일한 안정성 확보
- 동일한 확장성 확보
- 낮은 학습 비용
- 낮은 유지보수 비용

### 적용 방식

초기 구현에서는 문제를 직접적으로 해결한다.

다만 단순 구현이 다음 문제를 만들기 시작하면 구조화를 검토한다.

- 중복 증가
- 변경 범위 확산
- 테스트 어려움
- 책임 혼합
- 예외 처리 누락
- 흐름 추적 어려움

### 경험 기반 사례

초기 운영 환경에서는 별도 DB 서버를 도입하지 않고 파일 기반 데이터베이스를 선택했다. 단일 인스턴스, 제한된 트래픽, 빠른 배포, 낮은 운영 복잡도가 더 중요한 조건이었기 때문이다.

다만 이 선택이 다중 인스턴스, 동시 접근, 정교한 마이그레이션에는 한계를 가진다는 점을 문서화했고, 향후 중앙 집중형 RDBMS 전환과 마이그레이션 체계 고도화를 개선 방향으로 남겼다.

이 사례는 단순한 구조가 항상 부족한 구조라는 뜻은 아니라는 것을 보여준다. 현재 조건에서 충분한 구조와 미래에 필요한 구조는 다를 수 있다.

### 예외

운영 안정성, 데이터 보존, 장애 복구와 관련된 영역은 단순함만을 기준으로 판단하지 않는다.

단순하지만 위험한 구조보다 조금 복잡하더라도 안전한 구조를 선택한다.

---

## 9. 추상화는 비용이 있는 작업이다

### 원칙

모든 추상화는 학습 비용과 유지보수 비용을 가진다.

따라서 추상화는 미래의 중복 제거 가능성과 변경 비용 감소 효과가 있을 때만 도입한다.

추상화는 코드를 멋있게 보이게 하기 위한 장치가 아니다.

### 판단 기준

다음 상황에서는 추상화를 검토한다.

- 중복 구현이 반복된다
- 구현체가 여러 개 존재한다
- 변경 가능성이 높다
- 테스트가 어려워진다
- 외부 의존성을 격리해야 한다
- 정책과 구현을 분리해야 한다

### 적용 방식

처음부터 추상화하지 않는다.

구체적인 구현을 통해 문제의 형태를 파악한 뒤, 반복되는 패턴이 확인되면 추상화한다.

### 경험 기반 사례

외부 서비스, 저장소, 알림, 설정 로딩처럼 변경 가능성이 높은 경계는 별도 모듈로 분리하는 방향을 잡았다. 다만 모든 기능을 처음부터 추상화하지는 않았다.

실제 운영 중 반복적으로 변경되거나 장애 가능성이 높다고 확인된 부분부터 분리 기준을 강화했다. 이 경험을 통해 추상화는 설계 감각만으로 도입하는 것이 아니라, 변경 압력과 반복성을 근거로 도입해야 한다는 기준이 생겼다.

### 예외

외부 서비스, 저장소, 인증, 결제, 알림처럼 변경 가능성과 장애 가능성이 높은 경계는 초기에 추상화를 고려할 수 있다.

## 10. 기록은 미래의 자신을 위한 투자다

### 원칙

시간이 지나면 대부분의 의사결정 이유는 잊힌다.

코드는 무엇을 했는지는 보여준다. 하지만 왜 그렇게 했는지는 보여주지 않는다.

중요한 의사결정은 기록한다.

기록은 과거를 설명하기 위한 것이 아니다. 미래의 수정 비용을 줄이기 위한 것이다.

### 프로젝트에서 드러나는 일반적인 상황

시간이 지나면 다음 정보들이 기억에서 사라진다.

- 왜 이 구조를 선택했는가
- 왜 다른 방법을 버렸는가
- 당시 어떤 제약이 있었는가
- 어떤 문제를 해결하려고 했는가
- 어떤 한계를 알고도 감수했는가
- 나중에 어떤 방향으로 개선하려 했는가

반대로 기록이 남아 있는 결정은 몇 달이 지나도 다시 이해하는 비용이 낮다.

### 기록 대상

다음 내용은 기록할 가치가 높다.

- 기술 선택 이유
- 구조 선택 이유
- 폐기한 대안
- 알려진 한계
- 향후 개선 계획
- 운영 중 발생한 문제
- 재발 방지 판단
- 임시 조치의 이유

### 적용 방식

모든 사소한 결정을 기록하지 않는다.

다음 조건 중 하나라도 해당하면 기록을 고려한다.

- 나중에 다시 논의될 가능성이 있다
- 선택지가 여러 개였다
- 단점이 있지만 선택했다
- 프로젝트 구조에 영향을 준다
- 운영 방식에 영향을 준다
- 다른 사람이 맥락을 알아야 한다

### 경험 기반 사례

기능 변경 기록, 장애 대응 기록, DB 구조 변경 이유, 기존 대응 철회 이유, 향후 개선 방향을 남겼다. 특히 어떤 선택이 완전한 해결책이 아니더라도, 당시 왜 그 선택을 했는지 기록해두면 나중에 같은 문제를 다시 볼 때 판단 비용이 줄어든다.

이 경험을 통해 기록은 단순한 릴리즈 노트가 아니라, 미래의 리팩터링과 운영 판단을 위한 근거라는 기준을 갖게 되었다.

---

## 11. 프로젝트는 완벽하지 않다는 것을 전제로 한다

### 원칙

모든 프로젝트에는 제약이 존재한다.

- 시간
- 인력
- 경험
- 예산
- 일정
- 기술 부채
- 기존 구조
- 운영 환경

좋은 의사결정은 완벽한 선택이 아니다. 좋은 의사결정은 현재 조건에서 가장 합리적인 선택이다.

### 판단 기준

다음 질문을 사용한다.

- 지금 상황에서 가장 큰 리스크는 무엇인가
- 완벽한 해결보다 먼저 줄여야 하는 비용은 무엇인가
- 지금 해결하지 않아도 되는 문제는 무엇인가
- 나중에 해결해도 되는 문제는 무엇인가
- 현재 선택의 한계를 기록했는가

### 적용 방식

완벽한 설계보다 현실적인 개선을 우선한다.

다만 임시 조치는 임시 조치임을 명확히 한다. 임시 구조가 영구 구조처럼 굳어지지 않도록 한계와 개선 방향을 기록한다.

### 경험 기반 사례

파일 기반 데이터베이스, 단일 인스턴스 운영, 단순 프로세스 관리 방식은 이상적인 최종 구조라고 보기 어렵다. 하지만 당시 운영 규모와 요구 수준에서는 충분히 작동 가능한 구조였다.

대신 이 구조가 가진 한계를 숨기지 않고, 다중 인스턴스 대응, 중앙 집중형 RDBMS 전환, 로그 로테이션, 헬스체크, 롤백, systemd 기반 서비스 관리 같은 개선 방향을 문서에 남겼다.

이 경험을 통해 현재 선택의 한계를 아는 것이 현재 선택을 부정하는 것은 아니라는 기준을 갖게 되었다.

---

## 12. 기술보다 문제 해결을 우선한다

### 원칙

특정 기술은 목적이 아니다. 기술은 문제 해결을 위한 도구다.

새로운 기술을 사용하는 것 자체는 가치가 아니다. 기술 선택은 해결하려는 문제와 줄일 수 있는 비용을 기준으로 판단한다.

### 판단 기준

다음 질문을 사용한다.

- 이 기술이 해결하는 문제는 무엇인가
- 기존 방법보다 어떤 비용을 줄이는가
- 유지보수에 어떤 영향을 주는가
- 팀이 이해하고 운영할 수 있는가
- 장애가 발생했을 때 디버깅 가능한가
- 장기적으로 의존해도 되는가

### 적용 방식

기술을 선택할 때는 장점만 보지 않는다.

다음 비용도 함께 본다.

- 학습 비용
- 마이그레이션 비용
- 디버깅 비용
- 운영 비용
- 의존성 리스크
- 팀 적응 비용

### 경험 기반 사례

별도 DB 서버를 도입하지 않고 SQLite를 선택한 것은 기술적으로 가장 강력한 선택이어서가 아니라, 당시 문제를 가장 낮은 운영 비용으로 해결할 수 있는 선택이었기 때문이다.

마찬가지로 모든 첨부파일을 외부 서비스에 직접 업로드하지 않고 일부 파일을 링크로 대체한 것도 기술 구현 가능성보다 운영 비용과 리소스 사용량을 기준으로 판단한 결과였다.

---

## 13. 데이터는 나중에 다시 해석될 수 있다고 본다

### 원칙

현재는 단순 기록처럼 보이는 데이터도 나중에는 분석, 복구, 개선의 근거가 될 수 있다.

따라서 중요한 상태 변화와 사용자 요청, 시스템 처리 결과는 가능한 추적 가능하게 남긴다.

### 판단 기준

다음 질문을 사용한다.

- 이 데이터는 나중에 문제 원인을 찾는 데 필요한가
- 운영자가 상태를 확인할 수 있는가
- 실패 원인을 추적할 수 있는가
- 사용자 요청과 시스템 처리를 연결해서 볼 수 있는가
- 데이터가 너무 부족해서 나중에 판단할 수 없게 되지는 않는가

### 적용 방식

다음 정보는 가능한 기록 대상으로 본다.

- 요청 시점
- 처리 상태
- 실패 사유
- 외부 연동 결과
- 주요 상태 변화
- 사용자가 입력한 핵심 정보
- 시스템이 결정한 결과

### 경험 기반 사례

사용자 요청을 단순 메시지로 처리하지 않고, 상태를 가진 티켓 흐름으로 관리했다. 티켓 생성, 메시지 저장, 외부 서비스 동기화, 마감, 재오픈, 폐기 상태를 구분해 기록함으로써 사용자의 현재 상태와 운영자의 처리 상태를 함께 추적할 수 있도록 했다.

또한 마지막 상호작용 시간을 저장해 쿨다운 판단, 자동 마감 판단, 상태 추적에 사용할 수 있도록 했다. 이 경험을 통해 데이터는 단순 저장물이 아니라 이후 판단을 위한 근거가 될 수 있다는 기준이 강해졌다.

### 주의점

데이터를 많이 저장하는 것이 항상 좋은 것은 아니다.

보안, 개인정보, 저장 비용, 관리 비용을 함께 고려한다. 필요한 데이터를 남기되, 불필요하게 민감한 데이터를 저장하지 않는다.

---

## 14. 시스템 상태는 추적 가능해야 한다

### 원칙

운영 중인 시스템은 현재 무슨 일이 일어나고 있는지 확인 가능해야 한다.

기능이 동작하는 것만으로는 충분하지 않다. 상태를 확인할 수 없으면 장애를 이해할 수 없고, 장애를 이해할 수 없으면 복구할 수 없다.

### 판단 기준

다음 질문을 사용한다.

- 지금 시스템이 정상인지 확인할 수 있는가
- 특정 요청이 어디까지 처리되었는가
- 실패한 작업을 식별할 수 있는가
- 중복 처리 여부를 확인할 수 있는가
- 운영자가 문제 상황을 알아차릴 수 있는가

### 적용 방식

다음 요소를 고려한다.

- 상태값
- 로그
- 알림
- 처리 결과 저장
- 마지막 동기화 시점
- 실패 횟수
- 재시도 기록

### 경험 기반 사례

장애 대응 비용을 줄이기 위해 로그를 파일에만 남기지 않고 운영자가 확인하는 메신저 채널로도 전송했다. 오류 발생 시 요약 메시지와 상세 로그를 함께 남겨, 운영자가 서버에 직접 접속하기 전에 1차 상황을 파악할 수 있도록 했다.

또한 재시작 실패 시 최근 로그를 출력하도록 구성했다. 운영자가 실패 여부만 아는 것이 아니라, 실패 직후 무엇을 확인해야 하는지 바로 알 수 있도록 하기 위한 선택이었다.

---

## 15. 사용자 경험과 운영 경험을 함께 본다

### 원칙

좋은 시스템은 사용자에게만 편한 시스템이 아니다.

운영자와 개발자에게도 이해 가능하고 관리 가능해야 한다.

사용자 경험을 개선하면서 운영 경험을 과도하게 악화시키는 선택은 장기적으로 문제가 될 수 있다.

### 판단 기준

다음 질문을 사용한다.

- 사용자는 더 쉽게 사용할 수 있는가
- 운영자는 더 쉽게 관리할 수 있는가
- 문제가 생겼을 때 누가 어떻게 복구하는가
- 사용자 편의를 위해 운영 비용이 과도하게 증가하지 않는가
- 운영 편의를 위해 사용자 경험이 지나치게 나빠지지 않는가

### 적용 방식

사용자 흐름과 운영 흐름을 함께 설계한다.

사용자가 어떤 행동을 할지뿐 아니라, 그 행동이 시스템 내부에서 어떤 상태 변화를 만드는지도 함께 본다.

### 경험 기반 사례

티켓이 마감되었을 때 사용자가 채널을 완전히 볼 수 없게 만드는 대신, 채널 조회는 가능하게 두고 채팅 권한만 비활성화하는 방향으로 변경했다. 이는 사용자가 이전 대화 내용을 확인할 수 있게 하면서도, 운영 상태는 마감 상태로 유지하기 위한 선택이었다.

또한 첨부파일 처리에서는 사용자 편의와 서버 리소스 사이의 균형을 고려했다. 모든 파일을 외부 서비스로 업로드하는 대신, 이미지 파일은 직접 업로드하고 나머지는 원본 메시지 링크로 대체했다.

---

## 16. 외부 시스템과 내부 상태는 어긋날 수 있다고 본다

### 원칙

외부 서비스와 내부 저장소를 함께 사용하는 시스템에서는 양쪽 상태가 항상 일치한다고 가정하지 않는다.

외부 API 실패, 지연, 삭제된 리소스, 중복 이벤트, 부분 성공으로 인해 내부 상태와 외부 상태는 쉽게 어긋날 수 있다.

따라서 외부 연동 기능은 상태 확인, 재동기화, 무시 가능한 이벤트 판별, 실패 기록, 수동 복구 가능성을 함께 고려한다.

### 판단 기준

다음 질문을 사용한다.

- 외부 서비스에는 존재하지만 내부에는 없는 데이터가 생길 수 있는가
- 내부에는 존재하지만 외부 서비스에는 삭제된 데이터가 생길 수 있는가
- 같은 이벤트가 중복으로 들어오면 어떻게 되는가
- 외부 API가 일시적으로 실패하면 어떤 상태가 남는가
- 외부 상태와 내부 상태 중 어느 쪽을 기준으로 복구할 것인가

### 적용 방식

외부 연동 지점에서는 다음 요소를 고려한다.

- 외부 리소스 존재 여부 확인
- 내부 상태와 외부 상태 비교
- 삭제되거나 만료된 리소스 대응
- 중복 이벤트 무시
- 실패 원인 기록
- 수동 복구 가능성

### 경험 기반 사례

외부 API 응답이 항상 정상적이라고 가정하지 않았다. 외부 서비스에서 유효하지 않은 상태, 삭제된 사용자, 일시적 오류, 만료된 상호작용이 발생할 수 있다고 보고, 가능한 경우 로컬 상태를 확인한 뒤 재생성, 무시, 로그 기록 중 하나로 처리했다.

이 경험을 통해 외부 의존성은 단순한 호출 대상이 아니라 실패 가능성이 높은 경계라는 기준을 갖게 되었다.

---

## 17. 운영자가 수정해야 하는 것과 수정하면 안 되는 것을 분리한다

### 원칙

운영 환경에서는 모든 설정이 같은 위험도를 가지지 않는다.

자주 변경되는 실행 설정과 시스템 내부 동작 기준은 서로 다른 변경 이유를 가진다.

따라서 운영자가 수정해야 하는 값은 명확히 노출하고, 내부 구조에 영향을 주는 값은 별도 영역으로 분리한다.

### 판단 기준

다음 질문을 사용한다.

- 이 설정은 운영 중 변경될 가능성이 높은가
- 이 설정을 잘못 바꾸면 시스템 내부 구조가 깨지는가
- 운영자가 이해하고 수정할 수 있는 값인가
- 개발자가 관리해야 하는 내부 기준인가
- 설정 변경 책임이 명확한가

### 적용 방식

설정은 다음 기준으로 분리한다.

- 운영자가 변경해야 하는 런타임 설정
- 개발자가 관리해야 하는 내부 설정
- 외부 서비스 정책 변경 시에만 바뀌는 매핑 설정
- 시스템 경로와 기본 동작을 정의하는 기준 설정

### 경험 기반 사례

운영 환경에서 직접 수정 가능한 설정 파일을 제한하고, 내부 시스템 설정은 별도로 분리했다. 이 구조는 설정 변경의 자유도를 줄이기 위한 것이 아니라, 수정 책임과 위험도를 명확히 나누기 위한 선택이었다.

운영자가 자주 바꾸는 값과 개발자가 관리해야 하는 값을 같은 위치에 두면 실수로 내부 기준이 변경될 수 있다. 이 경험을 통해 설정 구조 자체도 운영 안정성의 일부라는 기준을 갖게 되었다.

---

## 18. 자동화는 실행뿐 아니라 실패 후 상태까지 고려한다

### 원칙

자동화는 작업을 대신 실행하는 것에서 끝나지 않는다.

자동화가 실패했을 때 어떤 상태가 남는지, 다시 실행해도 안전한지, 운영자가 원인을 확인할 수 있는지가 함께 설계되어야 한다.

### 판단 기준

다음 질문을 사용한다.

- 자동화가 중간에 실패하면 어떤 상태가 남는가
- 같은 자동화가 동시에 실행되면 문제가 생기는가
- 실패한 자동화를 다시 실행해도 안전한가
- 자동화 결과를 검증할 수 있는가
- 운영자가 실패 원인을 확인할 수 있는가
- 자동화가 실패했을 때 수동 복구할 수 있는가

### 적용 방식

시스템 상태를 바꾸는 자동화에는 다음 요소를 함께 고려한다.

- 중복 실행 방지
- 실행 전 상태 확인
- 실행 후 결과 검증
- 실패 로그 출력
- 재시도 가능성
- 수동 복구 절차

### 경험 기반 사례

배포 자동화에서 워크플로우 레벨의 동시 실행 제한과 서버 내부 배포 락을 함께 사용했다. 또한 재시작 스크립트는 기존 프로세스 종료, 강제 종료 fallback, 백그라운드 실행, 기동 검증, 실패 시 로그 출력까지 포함했다.

이 경험을 통해 자동화는 성공했을 때의 편의성보다 실패했을 때 남는 상태를 더 신중하게 봐야 한다는 기준을 갖게 되었다.

---

## 19. 유연성을 유지한다

### 원칙

현재의 판단 기준이 미래에도 항상 옳다고 가정하지 않는다.

새로운 경험과 정보는 기존 판단 기준을 바꿀 수 있다.

원칙은 존재하지만 교조주의는 지양한다. 좋은 원칙은 변하지 않는 규칙이 아니라 변화에 대응할 수 있는 기준이다.

### 판단 기준

다음 질문을 사용한다.

- 이 원칙은 지금 상황에도 유효한가
- 기존 방식보다 더 나은 방식이 발견되었는가
- 예외가 반복된다면 원칙을 수정해야 하는가
- 과거의 선택을 지키기 위해 현재의 문제를 무시하고 있지는 않은가

### 적용 방식

원칙은 계속 수정될 수 있다.

다만 수정은 감각만으로 하지 않는다. 반복된 경험, 실제 문제, 유지보수 비용, 운영 비용을 근거로 수정한다.

### 경험 기반 사례

초기에는 단순한 구현이 충분하다고 판단한 부분도, 운영 중 데이터 꼬임, 외부 API 오류, 동기화 문제, 배포 실패 가능성을 겪으면서 기준이 바뀌었다.

반대로 처음에는 필요해 보였던 작업도 실제 운영 조건에서 비용 대비 효과가 낮다고 판단되면 보류하거나 철회했다. 이 경험을 통해 원칙은 고정된 신념이 아니라, 실제 문제를 기준으로 계속 갱신되는 판단 도구라는 기준을 갖게 되었다.

---

## 20. 최종 목표

최종 목표는 가장 화려한 시스템을 만드는 것이 아니다.

가장 복잡한 시스템을 만드는 것도 아니다.

목표는 다음 조건을 만족하는 시스템이다.

- 이해하기 쉽다
- 수정하기 쉽다
- 운영하기 쉽다
- 확장하기 쉽다
- 실수에 강하다
- 실패를 추적할 수 있다
- 외부 상태와 내부 상태의 차이를 인지할 수 있다
- 자동화 실패 후에도 복구 가능하다
- 시간이 지나도 버려지지 않는다

좋은 설계는 미래의 자신과 미래의 협업자를 배려하는 설계다.

---

## 21. 요약

본 문서의 핵심은 다음과 같다.

- 구현 속도만 보지 않고 유지보수 비용을 함께 본다.
- 역할 이름보다 변경 이유를 기준으로 분리한다.
- 운영 비용은 개발 비용만큼 중요하게 본다.
- 사용자의 실수와 시스템 실패를 전제로 설계한다.
- 반복 작업은 자동화를 우선 검토한다.
- 자동화는 실행뿐 아니라 실패 후 상태까지 고려한다.
- 추상화는 필요할 때만 도입한다.
- 중요한 의사결정은 기록한다.
- 기술보다 문제 해결을 우선한다.
- 시스템 상태는 추적 가능해야 한다.
- 외부 시스템과 내부 상태는 어긋날 수 있다고 본다.
- 운영자가 수정해야 하는 것과 수정하면 안 되는 것을 분리한다.
- 원칙은 유지하되, 더 나은 근거가 생기면 수정한다.

---

## 22. 현재 문서의 성격

이 문서는 완성된 정답지가 아니다.

실제 프로젝트를 만들고 운영하면서 겪은 문제, 수정한 흐름, 보류한 개선점, 나중에 다시 고쳐야 한다고 판단한 부분을 바탕으로 정리한 현재의 의사결정 기준이다.

따라서 이 문서의 목적은 특정한 설계 방식을 절대화하는 것이 아니라, 앞으로 비슷한 선택을 해야 할 때 같은 실수를 줄이고 더 빠르게 판단하기 위한 기준을 남기는 것이다.

현재 기준에서 가장 중요한 태도는 다음과 같다.

> 완벽한 선택을 했다고 주장하지 않는다.
> 

> 다만 당시 조건에서 왜 그렇게 선택했는지 설명할 수 있어야 한다.
> 

> 그리고 더 나은 근거가 생기면 기존 선택을 수정할 수 있어야 한다.
